## 当前设计默认

| ADR | 默认选择 | 理由 | 何时重新评估 |
|---|---|---|---|
| 001 | Rust 控制面 + 标准 Git | 降低协议/存储引擎重写风险 | 有可测瓶颈或标准 Git 无法满足目标 |
| 002 | 模块化单体 + 仅 PostgreSQL 的队列/outbox | 用户确认只支持 PostgreSQL；不做 SQLite、MySQL 或其他数据库适配 | 用户明确改变数据库范围；队列负载/多地域需求已被实际数据证明 |
| 003 | 真实状态决定完成 | 提交、测试、部署都需要可验证证据 | 不改变原则，只完善证据类型 |
| 004 | Compose 单主机为首个部署目标 | 限定部署适配成本，验证发布主线 | 试点明确要求 K8s 且愿意增加范围 |
| 005 | 同仓库 PR + merge commit | 简化权限、精确候选检查与审查关联 | fork/rebase/squash 成为明确迁入阻碍 |
| 006 | 单个实测 Agent + 开放适配契约 | 先证明一个可靠闭环 | 首个适配稳定后验证第二个实现的替换成本 |
| 007 | MCP 使用统一领域服务 | 避免界面与 Agent 权限不一致 | 保持原则；协议/工具分组可演进 |
| 008 | 本地 BlobStore + 外部 OCI Registry | 不同时开发完整对象存储与包注册平台 | 存储规模/可用性需要 S3 或分布式存储 |
| 009 | 首版 stdio / 预配置 HTTP token MCP | 明确首轮客户端范围 | 需要 OAuth 客户端时单独实现资源服务器互操作 |
| 010 | 生产环境批准、自动测试环境交付 | 保留自动化同时控制环境修改边界 | 按组织风险与实测记录逐步调整策略 |

## 变更管理

任何影响首版 P0、权限边界、数据不可变性、API 兼容或交付日期的变更都更新本记录、PRD、MCP/数据库相关章节和开发计划。范围变更需要明确提出，不以实施细节名义悄悄取消已确认目标。

文档基线 0.1 不是正式产品版本。首次代码实现开始后，前后端版本、响应 header、Changelog 和产品概览采用同一版本源。
