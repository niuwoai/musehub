# MuseHub 产品需求与首版验收

> 文档基线 0.1｜2026-10-30｜目标 `0.1.0-rc1`。本文描述计划行为，不代表已实现。

## 1. 问题与目标

团队目前往往需要在 Git 平台、Agent 工具、CI、镜像仓库和部署系统之间人工搬运上下文。MuseHub 将需求版本、执行记录、代码变更、测试证据、发布制品和环境状态关联起来，减少交接遗漏，并让失败可定位、任务可恢复。

首版目标是一个内网团队可持续试用的交付闭环。完整 Git 托管平台是长期目标；首版通过明确支持矩阵实现基本互操作，不以“完整”暗示支持所有扩展协议和协作特性。

## 2. 用户与核心场景

| 角色 | 目标 | 主要入口 |
|---|---|---|
| 需求发起人 | 描述问题与验收条件，跟踪交付 | Issue、计划、交付时间线 |
| 开发者 | 自己开发或交给 Agent，查看失败原因 | 仓库、PR、AgentRun、CI |
| 审查者/维护者 | 审查变更与证据，决定合并与发布 | PR、检查、Release |
| 运维/发布者 | 管理环境与部署，恢复异常版本 | 环境、部署、Runner |
| 管理员 | 用户、权限、密钥引用、配额、备份 | 管理控制台 |
| 外部 Agent/MCP 客户端 | 在授权边界内完成研发操作 | MCP / Git / REST |

### S1：人工开发

创建 Issue → 本地 git clone → push 分支 → 创建 PR → CI → 人工审查 → 合并 → 合并后构建 → Release → 部署。即使没有可用模型，所有人工路径仍可用。

### S2：Agent 实现

保存需求版本与验收条目 → 保存计划 → 用户接受计划并启动执行 → 生成独立分支与工作空间 → Agent 产生提交 → 平台验证远端分支与 diff → 创建草稿 PR → CI 和审查 → 按反馈启动新一轮执行。任务需要输入时进入等待状态，不能假装成功。

### S3：失败修复

PR 的 CI 失败 → 在 PR 中显示失败摘要、日志定位和关联 job → 用户点击“交给 Agent 修复” → 在当前 head 上新建执行轮次。首版不默认自动触发无限自修复；同一根因链、预算和最大轮次必须有上限。

### S4：发布与部署

维护者选取已通过检查的合并后 commit → 创建 Release 草稿 → 构建并绑定制品摘要 → 发布固定 tag → 部署测试环境 → 检查健康 → 如失败显示故障并提供回滚。受保护环境必须有有效的环境审批。

## 3. V1 必须交付的功能

优先级 P0 表示发布门禁；P1 表示后续版本，不以时间紧张为由静默删除 P0。

| 编号 | P0 能力 | 验收要求 |
|---|---|---|
| IAM-01 | 本地登录、组织成员、固定角色、会话撤销 | 禁用用户后新请求与新 Git 会话被拒绝；退出后会话失效 |
| IAM-02 | PAT、SSH key、服务/Agent 身份 | PAT 有期限、scope、仓库限制；只展示一次明文；key 可撤销 |
| IAM-03 | 授权与审计 | Web/REST/MCP/Git 结果一致；跨组织 ID 猜测不能读取数据 |
| GIT-01 | 私有仓库创建、空仓库、默认分支 | 初始化失败可重试；用户路径不能决定磁盘绝对路径 |
| GIT-02 | HTTPS/SSH clone、fetch、push | 标准 Git 客户端端到端通过；拒绝交互式 SSH shell |
| GIT-03 | 文件、目录、提交、历史与 diff | 固定到 commit；二进制/大文件显示元数据并限制渲染 |
| GIT-04 | 保护分支和标签 | 直推、删分支、force push、HTTP/SSH/API 合并统一受控 |
| GIT-05 | 手动迁入与备份恢复 | 支持客户端 mirror push 迁入 Git refs；完整恢复演练通过 |
| ISS-01 | Issue CRUD、讨论、标签、一个负责人 | 仓库内唯一编号；列表筛选与游标分页；关闭原因明确 |
| ISS-02 | 需求版本、验收条目、计划 | 启动执行冻结版本与计划；编辑不改变已有任务依据 |
| PR-01 | 同仓库分支 PR、diff、行评论、审查 | 评论绑定 diff 版本，旧位置显示过期；作者不得自我批准 |
| PR-02 | 门禁与合并 | 审查绑定 head；base/head 改变使旧候选检查失效；V1 只支持 merge commit |
| AGT-01 | 一个真实 Agent 适配器 | 可配置外部端点和凭据引用；用真实小任务生成非空提交与 PR |
| AGT-02 | 排队、状态、日志、取消、反馈、重试 | 不丢任务；重复请求不重复启动；取消停止执行并撤销凭据 |
| AGT-03 | 执行边界 | 独立工作空间、分支限制、时限、步骤上限、预算与来源记录 |
| CI-01 | YAML DAG、push/PR/manual/tag 事件 | 校验循环依赖/未知字段；冻结工作流来源 commit 与 hash |
| CI-02 | Linux Runner、并行 job、日志、超时、重试 | 服务或 Runner 重启后的状态可解释；过期 Runner 不可回写成功 |
| CI-03 | 缓存、制品、测试报告 | 校验摘要、限制大小、租户隔离；缓存不作为唯一正确性依据 |
| REL-01 | 草稿、发布说明、tag、Release 资产 | Release 固定 commit 与资产 digest；重复发布返回同一操作 |
| DEP-01 | Compose 部署、环境状态、健康检查 | 从 Registry 按 digest 拉取；确认实际运行 digest；失败有证据 |
| DEP-02 | 环境审批、串行部署、回滚 | 审批绑定目标制品/配置；同环境同时最多一个变更操作 |
| MCP-01 | 研发工具与资源 | 支持鉴权、分页、幂等、结构化返回及业务错误；覆盖 S1–S4 |
| OPS-01 | 安装、升级、恢复、版本与观测 | `X-App-Version` 一致；备份恢复后权限、refs、制品关系有效 |
| UI-01 | 工具型 Web、中英文 i18n | 必需流程可从 Web 完成；无新增硬编码展示文案；键盘可操作 |

### 明确排除的 V1 范围

| 后续能力 | 原因/首版替代 |
|---|---|
| 纯 Rust Git 协议/对象引擎 | 标准 Git 作为隔离基础工具，优先确保互操作与数据完整性 |
| Git LFS、partial clone 服务保证、SHA-256 仓库 | 首版只验收普通 SHA-1 仓库；超范围返回明确错误，不静默损坏 |
| 跨仓库 fork PR、PR rebase/squash、merge queue | 同仓库分支 + merge commit；服务端串行化保护分支写入 |
| 持续镜像与完整平台迁移 | 支持 Git refs 手动迁入；Issue/PR 历史迁移另立项目 |
| 任意 GitHub Actions `uses` 兼容 | 自有版本化 YAML，只支持明确的步骤与参数 |
| cron 调度、构建矩阵、服务容器、可复用 workflow | 首版 push/PR/manual/tag 触发与基本 DAG；这些高级流水线能力后续扩展 |
| Windows/macOS Runner、多地域 HA | 首版 Linux 单控制面；明确备份恢复能力 |
| K8s/Helm、蓝绿/金丝雀、多服务发布编排 | 首版单主机 Compose；不承诺零停机 |
| 内建 OCI/通用包注册表 | 复用外部私有 Registry；平台存 Release 元数据与普通资产 |
| SAML/SCIM、复杂自定义角色 | 本地账号 + 固定角色；企业 IdP 进入下一阶段 |
| 多 Agent 自治团队、向量检索、IDE | 单执行链 + 反馈轮次；文件与精确文本搜索 |

## 4. 权限模型

组织角色为 owner/admin/member；仓库角色为 reader/developer/maintainer；environment deployer 是单独授权。站点管理员管理基础设施，不自动获得静默绕过仓库保护的入口；紧急操作必须是显式且可审计的维护模式。

| 操作 | Reader | Developer | Maintainer | 环境 Deployer |
|---|---|---|---|---|
| 读仓库、Issue、PR、脱敏日志 | ✓ | ✓ | ✓ | 按仓库授权 |
| 创建 Issue、评论 | — | ✓ | ✓ | 按仓库授权 |
| push 非保护分支、创建 PR、启动普通 CI | — | ✓ | ✓ | 按仓库授权 |
| 启动 Agent（另需 Agent 使用授权和配额） | — | ✓ | ✓ | — |
| 提交审查 | — | ✓ | ✓ | — |
| 合并保护分支、发布 Release、修改仓库规则 | — | — | ✓ | — |
| 执行部署/回滚 | — | — | 另需环境授权 | ✓ |
| 批准受保护环境 | — | — | 另需审批者授权 | 不能自行批准自己的部署 |

Agent 有独立服务身份。有效权限是发起人、Agent 身份、令牌 scope、仓库/环境策略的交集；后台执行前再次核对权限。首版 Agent 不担任最终人类批准者。

## 5. 状态与交付口径

- Issue：`open → in_progress → in_review → resolved/closed`。resolved 表示要求的代码与验收已完成；部署状态另行展示。重新打开必须保留旧交付记录。
- Plan：`draft → accepted → superseded`。接受绑定需求版本；不可原地改写被执行计划。
- AgentRun：`queued → running → waiting_input / succeeded / failed / cancel_requested → canceled`；等待后恢复建立新 attempt，取消请求不是终态。
- PR：`draft → open → merged/closed`；新提交撤销旧 head 的审批效力。
- Release：`draft → publishing → published / failed`；已发布资产不可原地替换，后续只能撤回分发或发布新版本。
- Deployment：`awaiting_approval → queued → running → healthy/failed/unknown/canceled`；回滚是另一条部署记录，不擦掉失败历史。

任务重试不等于继续同一个进程；每次 attempt 记录输入与结果。网络断开时若无法证明部署结果，必须显示 unknown 并对账，不能直接再部署一次。

## 6. 产品交互要求

- Issue 顶部突出验收标准与负责人，时间线链接计划、执行、PR、Release、部署。
- AgentRun 展示当前阶段、输入需求版本、base SHA、预算、最近进度和可执行的失败原因。
- PR 将 diff、讨论、检查和批准并置；大 diff 按文件加载，过期审查明显标注。
- Release 展示 source commit、构建 job、资产 digest、发布说明与环境状态。
- 环境页面同时展示“期望版本”和“最近观察到的实际版本”，保留观察时间。
- 普通开发者看到可理解的错误及操作；完整诊断 ID、错误码和技术细节放详情。

## 7. 非功能验收目标（待 M0 实测校准）

| 项目 | 首版设计目标 | 测试条件/限制 |
|---|---|---|
| 基础规模 | 50 用户、100 仓库、10 并发 job | 控制面 4 vCPU/8 GiB、SSD；Runner 资源另计 |
| 仓库大小 | 首轮支持与测试 2 GiB 以下普通仓库 | 不代表更大仓库不能工作；超过上限需配置与专项验证 |
| API 延迟 | 非 Git/搜索/大 diff 操作 p95 < 300ms | 内网、100 RPS、预热数据集，记录真实结果 |
| 调度延迟 | 有空闲 Runner 时 p95 < 5s | 不包含镜像下载、模型首 token 与依赖安装 |
| 持久性 | 已接受任务重启后不丢；重复投递无重复业务副作用 | kill server/runner、网络分区、数据库断连注入 |
| 初始恢复目标 | RPO ≤ 24h，RTO ≤ 4h | 试点数据集、每日完整一致性备份、实测恢复时间；不是 SLA |
| 安全边界 | 越权/分支绕过/凭据明文泄露测试全部通过 | 日志脱敏不替代执行隔离；CI 与生产凭据分开 |
| 可用性 | 无模型时人工研发可用 | 已启动 AgentRun 明确失败或等待，不影响 Git |

## 8. 首版最终验收剧本

1. 创建组织、维护者、开发者、只读用户、独立 Agent 身份和测试环境。
2. 创建仓库，用两个普通 Git 客户端经 SSH/HTTPS clone、push、fetch。
3. 创建带三个可验证验收条目的 Issue，保存计划并启动 Agent。
4. 修改 Issue 后确认已有 AgentRun 仍指向原需求版本；追加任务时显式选择新版本。
5. 生成非空提交与 PR，CI 运行；Reviewer 添加反馈，再执行一轮并更新 PR。
6. 故意引入测试失败，确认禁止合并；新提交后确认旧批准、旧合并候选检查不能放行。
7. 合并后对实际合并 commit 重建并测试，生成 OCI digest 和 Release 资产。
8. 发布 Release 并部署测试环境；观察运行 digest、健康结果和 Issue 时间线。
9. 部署一个不健康版本，完成回滚；确认旧制品、配置引用和回滚记录完整。
10. 期间注入重复 MCP 请求、控制面重启、Runner 丢失、取消与迟到结果；确认一致性。
11. 从备份恢复到全新隔离环境，复核 refs、权限、Release、制品和审计。

AI 质量评估使用冻结的 20 个小型真实任务（修复/小功能/测试各有覆盖），记录有效 PR 比例、人工返工时间、费用和完成率。先建立基线再设门槛；不能用虚构目标成功率宣传产品能力。
